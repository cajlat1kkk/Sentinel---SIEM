# Как проверить DPDK и VPP

Начните с лаборатории на Linux без физических сетевых карт. DPDK читает и пишет настоящие PCAP через `net_pcap`; VPP пересылает те же кадры между двумя программными интерфейсами. Эти проверки не требуют подключения к Интернету, root, настройки hugepages или изменения сетевых интерфейсов. Установленные зависимости требуются заранее.

Все команды ниже выполняются из корня проекта. Windows-приложение не содержит локальный Linux dataplane; эти проверки запускаются на Linux-машине или в Linux VM.

## 1. DPDK: обнаружение и фактическая блокировка

Соберите сенсор с установленными development-пакетами DPDK и PCAP PMD:

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DSIEM_WITH_DPDK=ON
cmake --build build -j 4
python3 scripts/test-dpdk.py
```

Проверка использует три безопасных синтетических HTTP-кадра: обычный запрос, SQL injection и XSS. Доступ к реальному веб-серверу не нужен. Критерии успеха:

| Сценарий | Принято | Обнаружений HTTP | Переслано | Отброшено |
|---|---:|---:|---:|---:|
| Мониторинг | 3 | 2 | 0 | 0 |
| Inline с HTTP-проверкой | 3 | 2 | 1 | 2 |
| Inline с правилом drop для HTTP | 3 | 2 | 0 | 3 |

Скрипт проверяет выходные PCAP: в первом inline-сценарии проходит только обычный запрос, в блокирующем — ни один. Строки `PASS` и код выхода `0` означают успешное завершение всех сценариев. Дополнительные проверки политики могут выводить дополнительные `PASS`.

Чтобы увидеть исходные события и счётчики вручную:

```bash
./build/siem-dpdk --pcap "$PWD/samples/http-lab.pcap" --seconds 2
```

В JSON-выводе ожидаются `packets: 3`, `alerts: 2`, `dropped: 0` и `forwarded: 0`: это режим мониторинга. В GUI откройте раздел сетевого движка и выберите `samples/http-lab.pcap`. После завершения анализа события должны появиться в списке событий, а счётчики — в карточке DPDK. Само чтение PCAP не проверяет драйвер физической NIC или производительность линии.

`net_pcap` — штатный программный драйвер DPDK; параметры `rx_pcap` и `tx_pcap` направляют RX/TX в файлы. Подробнее: [DPDK 25.11, PCAP PMD](https://doc.dpdk.org/guides-25.11/nics/pcap_ring.html).

## 2. VPP: подготовка

Нужны настоящие `vpp` и `vppctl` одной версии:

```bash
command -v vpp
command -v vppctl
```

Если их нет, тест завершится сообщением «Тест не выполнен». Наличие библиотеки DPDK само по себе не устанавливает VPP. Для Ubuntu/Debian используйте пакеты из [официального репозитория FD.io](https://packagecloud.io/fdio/release) для своей версии дистрибутива и [инструкцию FD.io по установке](https://docs.fd.io/vpp/25.10/gettingstarted/installing/ubuntu.html). Проверяйте перечень поддерживаемых дистрибутивов в репозитории; не устанавливайте Ubuntu-пакеты непосредственно на Arch. На Arch/CachyOS можно использовать сборку VPP из официальных исходников либо отдельную Ubuntu VM.

Для этой лаборатории достаточно ядра VPP и `vppctl`. DPDK-плагин VPP отключён в лабораторной конфигурации. При установке полного пакета VPP на отдельную VM проверьте автозапуск его системной службы: лабораторный скрипт запускает собственный экземпляр и не использует `/etc/vpp/startup.conf`.

На текущей машине доступна локальная сборка в `.dev/vpp-build`. Чтобы воспроизвести её после чистого checkout:

```bash
bash scripts/build-vpp-lab.sh
```

Скрипт скачивает официальный VPP v25.10 с проверкой SHA-256, создаёт Python venv для генератора API и собирает только VPP core/vppctl без плагинов. Нужны Clang, CMake, Ninja, Python с venv/pip, curl, tar и development-файлы OpenSSL/libunwind. Сборка использует инструкции текущего CPU и предназначена для локальной лаборатории. Системные пакеты, службы и сетевые настройки не меняются. Дальнейшие команды автоматически находят эту сборку.

### Системная установка на текущей машине CachyOS

30.10.2026 локальная сборка VPP 25.10 core/vppctl установлена отдельно от проекта в `/opt/sentinel-vpp/25.10`. Команды доступны через `/usr/local/bin/vpp` и `/usr/local/bin/vppctl`; библиотеки загружаются из каталога установки. Это ручная установка лабораторной сборки, не пакет pacman и не полный набор плагинов VPP.

Служба `vpp.service` включена в автозапуск. Она запускается от пользователя рабочего стола, использует `/etc/vpp/startup.conf` и создаёт `/run/vpp/cli.sock`. Каталог сокетов доступен только этому пользователю и root. В GUI в поле CLI-сокета укажите `/run/vpp/cli.sock` и запросите состояние.

```bash
command -v vppctl
systemctl status vpp.service --no-pager
vppctl show version
vppctl -s /run/vpp/cli.sock show interface
```

Физические NIC не подключены, плагины отключены. После запуска виден только `local0`; это исправное подключение к CLI, а не подтверждение мониторинга сетевого трафика. PCAP-проверку ниже можно запустить отдельно с установленными бинарниками:

```bash
bash scripts/test-vpp.sh --vpp /usr/local/bin/vpp --vppctl /usr/local/bin/vppctl
```

Этот тест создаёт собственный экземпляр и не меняет конфигурацию работающей службы. Управление службой: `sudo systemctl restart vpp` для перезапуска, `sudo systemctl disable --now vpp` для остановки и отключения автозапуска. Unit находится в `/etc/systemd/system/vpp.service`. На другой машине эту установку нужно выполнить отдельно; одного checkout проекта недостаточно.

## 3. VPP: тест реальной пересылки без NIC

```bash
bash scripts/test-vpp.sh
```

Если VPP собран в отдельном каталоге:

```bash
bash scripts/test-vpp.sh \
  --vpp /путь/к/build/bin/vpp \
  --vppctl /путь/к/build/bin/vppctl
```

Скрипт запускает VPP отдельным дочерним процессом, создаёт `pg0` и `pg1`, включает L2 xconnect в обе стороны между `pg0` и `pg1`, воспроизводит три кадра и сохраняет выходной PCAP. Успех проверяется по завершению генератора, счётчикам интерфейсов и побайтовому совпадению всех трёх выходных кадров с входными. В конце:

```text
PASS: VPP pg0 → L2 xconnect → pg1: 3 Ethernet-кадра; выходной PCAP совпадает побайтно.
```

В `show packet-generator` поток `sentinel` должен иметь `Enabled: No`, `Count: 3`; в `show interface` интерфейсы `pg0` и `pg1` находятся в состоянии `up`, с RX/TX-счётчиками. Это проверяет VPP dataplane и доступ к CLI; NGFW-правила приложения через этот адаптер в VPP не устанавливаются. Все три кадра проходят через L2 xconnect, включая тестовые строки SQLi/XSS.

Конфигурация основана на [samples/vpp-lab.conf](../samples/vpp-lab.conf): 256 МБ main heap, обычные страницы 4 КБ, 2048 буферов на NUMA, отдельные CLI/API/stats-сокеты в `/tmp/sentinel-vpp-*`, все плагины отключены. Короткая пауза в цикле опроса ограничивает нагрузку лаборатории; этот режим не подходит для измерения пропускной способности. Скрипт выбирает доступное процессу CPU и не запрашивает real-time приоритет.

Команды и параметры сверены с [FD.io Packet Generator CLI](https://docs.fd.io/vpp/25.10/cli-reference/clis/clicmd_src_vnet_pg.html), [официальным примером PCAP replay](https://wiki.fd.io/view/VPP/How_To_Use_The_Packet_Generator_and_Packet_Tracer) и [конфигурацией VPP](https://docs.fd.io/vpp/25.10/configuration/reference.html).

## 4. Подключение desktop-приложения к лабораторному VPP

Оставьте лабораторию работающей:

```bash
bash scripts/test-vpp.sh --serve
```

После `PASS` скрипт напечатает точный путь вида `/tmp/sentinel-vpp-XXXXXXXX/cli.sock`. В приложении откройте сетевой движок → VPP, вставьте этот путь в поле CLI-сокета и нажмите получение состояния. Ожидаются статус «Подключён» и интерфейсы `pg0`, `pg1` со счётчиками. Проверить тот же сокет вручную можно командой, которую напечатает скрипт:

```bash
vppctl -s /tmp/sentinel-vpp-XXXXXXXX/cli.sock show interface
```

Приложение ищет `vppctl` в `PATH`. При отдельной сборке VPP запустите GUI из терминала, где каталог с `vppctl` добавлен в `PATH`:

```bash
PATH="$PWD/.dev/vpp-build/bin:$PATH" ./build/sentinel-siem
```

Остановка: нажмите **Ctrl+C в терминале лаборатории**. Скрипт завершит только созданный им VPP, удалит свои временные файлы и собственные именованные SHM-сегменты. Обычный запуск без `--serve` выполняет эту очистку автоматически после проверки. В GUI последующий опрос покажет отсутствие подключения.

## 5. Проверка на выделенном оборудовании

Для аппаратной проверки нужен отдельный лабораторный Linux-хост, поддерживаемая [DPDK сетевая карта](https://core.dpdk.org/supported/nics/), выбранный драйвер, права доступа и подготовленная память. Пассивному сенсору нужен SPAN/TAP-порт; inline-режиму — два выделенных порта и генератор трафика. Параметры привязки PCI и hugepages зависят от NIC и ОС, поэтому лабораторные скрипты их не меняют.

Один PCI-порт не может одновременно принадлежать отдельному `siem-dpdk` и DPDK-плагину VPP. Проверяйте их по очереди либо выделите разные порты. Совместное соединение через memif/vhost потребовало бы отдельной реализации; в текущем приложении его нет.

Для подготовленного VPP получите реальные интерфейсы и счётчики:

```bash
vppctl -s /run/vpp/cli.sock show version
vppctl -s /run/vpp/cli.sock show plugins
vppctl -s /run/vpp/cli.sock show hardware-interfaces
vppctl -s /run/vpp/cli.sock show interface
vppctl -s /run/vpp/cli.sock show errors
```

Факт загрузки `dpdk_plugin.so` проверяется в `show plugins`, обнаруженные аппаратные порты — в `show hardware-interfaces`, поступление и пересылка трафика — по росту RX/TX и внешнему принимающему узлу. Сравните счётчики до и после подачи известного количества кадров. Одного статуса «Подключён» в GUI недостаточно для подтверждения пересылки через физические порты.

## Если проверка не проходит

| Сообщение | Что проверить |
|---|---|
| `siem-dpdk` отсутствует | Установлены ли DPDK development-пакеты; создала ли CMake цель сенсора |
| `net_pcap` / `no ports` | Установлен ли PCAP PMD и его libpcap-зависимости; существует ли входной PCAP |
| Ошибка привязки CPU | Скрипты автоматически выбирают доступное CPU; в ручных EAL-параметрах учитывайте cpuset контейнера |
| `vppctl не установлен` | `vppctl` должен находиться в `PATH` именно процесса GUI |
| VPP не создал сокет | Скрипт напечатает последние строки журнала VPP: проверьте совместимость CPU, память и библиотеки |
| Permission denied / тайм-аут CLI | Проверьте путь и права сокета; запускайте GUI и лабораторию одним пользователем |
| `unknown input` | Проверьте совпадение версий VPP/vppctl и поддержку команд; скрипт завершится ошибкой, а не `PASS` |
| RX растёт, TX нет | В мониторинге DPDK это ожидаемо; в VPP проверяйте состояние портов, L2/L3-настройку и `show errors` |

Лабораторные PCAP-проверки подтверждают конкретные сценарии, а не производительность или полноту промышленного NGFW. DPDK-анализ HTTP ограничен содержимым отдельных пакетов: без TCP reassembly, TLS-дешифрования и анализа всех протоколов. VPP-адаптер приложения читает телеметрию через CLI; управление ACL/NAT VPP в нём не реализовано.
