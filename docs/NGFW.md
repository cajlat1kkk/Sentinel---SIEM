# Настройка NGFW

Раздел **Правила → Firewall / NGFW** содержит отдельные профили Linux, DPDK и Windows. Каждый профиль сохраняется в PostgreSQL. Сохранение не применяет правила к ОС и не перезапускает сенсор.

## Возможности движков

| Настройка | Linux / nftables | DPDK inline | Windows Firewall |
|---|---|---|---|
| Направления | input / output / forward | forward | input / output |
| IPv4 / IPv6, CIDR | Да | Да | Да |
| TCP / UDP, порты и диапазоны | Да, источник и назначение | Да, источник и назначение | Да, local / remote |
| ICMP | Да, IPv4/IPv6 | Да | Отклоняется |
| Порядок правил | Первое совпадение | Первое совпадение; HTTP-блокировка раньше L3/L4 | Блокировка имеет приоритет |
| Действия | accept / drop / reject | accept / drop | allow / block |
| Политика по умолчанию | accept / drop для каждого направления | accept / drop для forward | Глобальная политика ОС сохраняется |
| Conntrack | established/related разрешены, invalid отброшен | Нет | Работает механизм самой ОС |
| Интерфейсы | Входной / выходной | Пока нет | Пока нет |
| Лимит пакетов в секунду | Для accept; превышение блокируется | Нет | Нет |
| NAT IPv4 | DNAT / SNAT / masquerade | Нет | Нет |
| SQL injection / XSS / path traversal | Отдельный профиль DPDK | Выбор сигнатур, block / alert | Отдельный Linux-сенсор |
| HTTP Host | Отдельный профиль DPDK | Домен или `*.example.org` | Отдельный Linux-сенсор |
| Журнал | nft log в журнал ядра, до 10 записей/с на правило | События JSON → SIEM, до 500 событий/с | Журнал аудита операций |

Неподдерживаемые настройки отклоняются до применения. Неизвестные поля JSON также отклоняются. В текущем MVP нет TLS-дешифрования, TCP reassembly, VPN, коммерческих категорий URL, защиты процессов и управления ACL VPP. Сигнатуры HTTP проверяют отдельные пакеты: это ограниченная проверка содержимого, которую можно обойти фрагментацией/сегментацией запроса. Она не заменяет полноценный IPS.

## Порядок работы

1. Выберите профиль нужного движка.
2. Добавьте сетевые правила: направление, адреса/CIDR или `any`, протокол, порты источника и назначения, действие. Списки портов: `80,443,8000-8080`. Изменяйте порядок кнопками ↑/↓, копируйте и выключайте правила.
3. Для Linux настройте политики по умолчанию, состояния соединений, журнал и NAT. Для DPDK выберите HTTP-сигнатуры, режим и домены. `example.org` совпадает точно; `*.example.org` — с поддоменами, без корневого домена.
4. Нажмите **Проверить и показать**. Для Linux показывается скомпилированный nftables batch; для остальных — проверенный JSON.
5. **Сохранить профиль** записывает черновик в PostgreSQL. **Применить к ОС** запускает отдельный helper через polkit / UAC и сообщает результат.
6. Для DPDK сохраните профиль и перезапустите сенсор в **Сетевом движке**. Даже анализ PCAP использует сохранённые настройки HTTP. Мониторинг создаёт события; блокировка действует только в inline с двумя портами.

Изменения другой консоли не перезаписываются молча: сохранение использует атомарное сравнение версии. История успешного применения и откат привязаны к компьютеру, черновики доступны консолям общей базы. При закрытии или смене профиля приложение предлагает сохранить изменения.

**Откатить применение** повторно применяет предыдущий успешно записанный профиль этого компьютера. Он доступен после двух успешных применений из этой версии консоли. Для снятия ограничений при первом применении можно очистить правила/NAT, выключить stateful и выбрать accept для всех направлений, затем применить этот профиль. Это изменяет только таблицы/правила Sentinel.

## Особенности эксплуатации

- Linux сначала запускает `nft --check`, затем применяет один атомарный batch. Управляются только `inet sentinel_siem` и `ip sentinel_siem_nat`; другие таблицы не очищаются. Accept в Sentinel не отменяет блокировку в другой таблице. Правила работают после закрытия GUI, но автоматически после перезагрузки Linux не восстанавливаются.
- Conntrack проверяется до пользовательских правил: уже отслеживаемое соединение остаётся разрешённым. Если нужно блокировать его немедленно, учитывайте это при выборе stateful; очистка глобального conntrack приложением не выполняется.
- Лимит действует на всё правило, а не отдельно на каждый IP. Первоначальный burst равен указанному числу пакетов в секунду.
- DNAT применяется в prerouting; к соединениям самого шлюза через output он не применяется. SNAT/masquerade работают в postrouting. Правило forward проверяет адрес назначения уже после DNAT.
- NAT не включает IP forwarding и не назначает адреса интерфейсам. Маршрутизацию и выделенные интерфейсы нужно подготовить отдельно. Физические интерфейсы автоматически не перенастраиваются.
- Windows применяет правила неатомарно. При ошибке возможен частично изменённый набор; проверьте состояние Windows Firewall и повторите применение. Правила Sentinel сохраняются средствами Windows.
- DPDK — прозрачный двухпортовый мост, без conntrack/NAT. При остановке процесса пересылка прекращается. Некорректные/неподдерживаемые кадры отбрасываются, корректный Ethernet/IPv4 ARP пропускается. IP-фрагменты не собираются; настройка блокировки фрагментов подчиняется режиму block/alert.
- Статус «Применялось» и время последнего применения — история операции, а не проверка текущего состояния firewall сторонними средствами.

## Воспроизводимые проверки

```bash
ctest --test-dir build --output-on-failure
bash scripts/test-postgres.sh
python3 scripts/test-dpdk.py
bash scripts/test-firewall-container.sh --host-runtime
```

Последняя команда использует отдельный Docker network namespace, NET_ADMIN и NET_RAW, образ `python:3.12-slim`, монтирование `/usr` и `build` только для чтения. Проверяются реальные UDP/TCP-пакеты, лимиты, conntrack, SNAT и DNAT через временную veth-пару внутри контейнера. Сеть и firewall хоста не изменяются.

Поведение Linux batch/цепочек сверено с [nftables manual](https://www.netfilter.org/projects/nftables/manpage.html), Windows COM — с [INetFwRules](https://learn.microsoft.com/en-us/windows/win32/api/netfw/nn-netfw-inetfwrules).
